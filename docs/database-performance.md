# 数据表性能边界

当前表格视图会完整创建行和单元格。一次本机 Chromium 测量使用 10,000 条记录、每条 3 个字段，三次样本的挂载中位数约 1.19 秒、单次文本输入约 118 毫秒、撤销约 1.18 秒、重做约 1.26 秒；页面中约有 140,092 个元素。另一次 CDP 测量得到约 350,000 个 DOM 节点、220,000 个监听器，渲染进程 RSS 约 1.43 GiB；该内存值包含浏览器和渲染开销，是单次样本，不代表数据表对象的独立大小。这些结果受机器、浏览器、字段和内容影响，不是性能承诺。

默认回归覆盖 100 和 1,000 条记录。一万行基准需要显式启用，每轮重新加载页面，最多运行三轮，并检查输入、撤销和重做结果：

```sh
SEMLO_DATABASE_10000=1 mise exec -- pnpm exec rstest run --config tests/config/rstest.config.ts --disableConsoleIntercept tests/features/database/database-performance.test.ts -t "measure 10000 database rows"
```

窗口渲染不能简单截取前若干行：隔离试验中，截取前 100 行虽降低了初次挂载成本，但未渲染记录无法滚动访问，全文查找定位和 Tab 顺序也被破坏。后续设计需同时处理筛选、分组、排序、固定行、拖拽、查找定位、键盘焦点、辅助技术、只读与导出，并验证文档替换、重入及撤销。

另一次试验省去单元格输入前的重复全表校验，最终事务仍保留完整校验；本机 10,000 行输入中位数约从 111 毫秒降至 101 毫秒。但宿主直接改动记录元数据后，冲突恢复若再次发生事务重入，之前已输入内容的撤销入口会丢失。该优化未合入；后续需要先设计可恢复的待提交历史，不能仅凭节点身份缓存校验结果。
