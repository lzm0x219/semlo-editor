# 软件设计与代码实现指南

本文面向设计、实现、重构和评审软件的开发者及智能体，覆盖从系统边界到具体代码的主要设计思想。它是**判断和查阅工具**：针对实际问题选择适用方法，并说明约束、收益、代价与验证证据；不要求项目使用全部范式、架构或模式。

软件工程没有一套适用于所有问题的最优解，本文也不声称穷尽全部研究成果。通用思想由下文提供依据和进一步阅读；Semlo 已有结构和维护约束以 [架构文档](architecture.md)、[AGENTS.md](../AGENTS.md) 和当前源码为准。文中的 TypeScript 和编辑器案例为独立示意，不宣称就是当前项目的实现或公开契约。

## 设计决策与质量属性

### 从需求到可检验的约束

设计之前区分：

1. **目标**：谁要完成什么，成功和失败分别表现为什么。
2. **约束**：平台、数据、接口、时间、资源及既有兼容性有哪些限制。
3. **不变量**：哪些关系必须在操作前后或可观察状态下保持成立，例如一条记录只能属于一个有效实例。
4. **变化与不确定性**：哪些需求有证据会变化，哪些只是猜测，错误假设的代价和撤回难度是什么。
5. **验收证据**：通过什么例子、检查或测量能区分满足要求和不满足要求。

例如，“编辑器性能好”不是可验证的要求。可以先定义文档规模、设备和操作，测量输入延迟及其分布，并说明目标与测量方法。不能从一次空文档测试推出大文档体验；性能目标必须由实际需求确定，不能把任意数字写成项目承诺。

### 质量属性与取舍

正确性、安全性、可用性、兼容性、可靠性、性能、可维护性和成本会相互影响。比较方案时，明确受益者、工作负载、失败后果和证据：

| 决策           | 获得的能力       | 需要承担的成本或风险         | 何时重新考虑                         |
| -------------- | ---------------- | ---------------------------- | ------------------------------------ |
| 保存派生结果   | 加快频繁读取     | 同步、失效和额外内存         | 数据规模或访问频率不足以抵消维护成本 |
| 引入扩展点     | 宿主可替换行为   | 契约、兼容、错误隔离和文档   | 没有真实调用方，或扩展边界尚不稳定   |
| 接受旧数据格式 | 减少用户迁移成本 | 解析和测试分支长期存在       | 格式有安全问题或已有明确迁移策略     |
| 异步处理       | 不阻塞当前流程   | 顺序、失败、取消和恢复更复杂 | 操作需要强顺序或即时反馈             |

先列出可行替代方案，再用相关质量属性比较。设计文档应记录约束和理由，而不是只宣布“采用某架构”；可逆的局部选择可轻量处理，影响数据或公开契约的选择需要更扎实的证据与迁移方案。

## 范式与设计原则

### 根据问题组合编程范式

编程范式描述组织计算的方式，而不是互斥的项目标签。同一编辑器可以用声明式组件描述工具栏，用事务表达状态变化，用纯函数处理规则，用事件响应输入。

| 范式              | 关注点与适用情况                                          | 代价与检查                                                   |
| ----------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| 命令式 / 过程式   | 顺序、循环和状态更新；适合具体流程及底层操作              | 检查修改顺序、共享状态和中途失败                             |
| 声明式            | 描述期望结果，由执行机制决定如何达到；适合 UI、查询和配置 | 确认隐藏的执行时序、性能和副作用                             |
| 面向对象          | 组织有身份、状态、行为及生命周期的对象                    | 控制可变状态和继承层次；保证替代实现的行为契约               |
| 函数式            | 函数组合、确定性计算、不可变值和显式副作用                | 适合规则与数据变换；大结构复制和过度组合可能有成本           |
| 事件驱动 / 响应式 | 通过事件或依赖变化协调处理                                | 明确顺序、重入、订阅清理、错误传播和追踪                     |
| 数据导向          | 根据数据布局和访问模式组织处理                            | 适合大量批量计算；需权衡局部性、可读性和封装                 |
| 并发 / 消息传递   | 将工作分给多个执行单元，通过同步或消息协作                | 明确共享、顺序、取消、背压与失败；消息传递不自动消除所有竞态 |
| 逻辑 / 约束式     | 描述事实、规则与满足条件的解                              | 适合约束求解；考虑求解成本、结果解释和边界                   |

范式的正确性取决于具体问题。局部纯函数可以让复杂规则更容易测试，但不要求将 DOM 或网络操作伪装成纯计算；对象能拥有资源，但不意味着所有数据都必须包装成类。

### 基本原则及其边界

- **关注点分离与高内聚**：围绕同一职责及共同变化的规则组织代码。共同使用同一份数据不一定意味着属于同一模块；总是一起变的代码也不应被机械拆散。
- **信息隐藏与封装**：让模块承担内部约束，向外暴露稳定能力，而不是要求调用方了解内部顺序和表示。隐藏实现不等于隐藏失败、成本或必要配置。Parnas 的模块划分研究将易变的设计决策作为重要考虑，见[论文](https://prl.khoury.northeastern.edu/img/p-tr-1971.pdf)。
- **组合与替换**：优先选择能够独立装配的能力；继承只有在子类型能满足原有调用方依赖的行为契约时才合适。相同签名不足以证明可替换，错误、时序和副作用也属于行为。
- **KISS、YAGNI、DRY**：选择满足需求的简单实现；没有证据的未来能力不预先建设；同一知识或规则应有清晰归属。相似代码不一定是同一知识，过早合并会把本应独立变化的规则绑在一起。
- **最小意外与显式依赖**：命名、返回值和副作用应符合调用方预期；依赖和所有权应能从接口或局部上下文发现。显式不等于把每个内部参数都变成公开 API。
- **控制副作用**：将规则计算与 I/O 等交互分清，确定状态改变的时机和所有者。某些行为天生有副作用，应把它们表达出来并管理生命周期。

### 函数式、契约与状态推理

**引用透明**意味着在相同上下文中，表达式可用其结果替代而不改变程序可观察行为。确定性、无可观察副作用的计算通常更容易复用和验证；读取当前时间、生成随机数、修改输入和访问网络都需要显式处理。可把时钟或随机源作为依赖传入，但只有在确实影响规则或测试时才需要增加这一层。

**契约式设计**把操作约定分为前置条件、后置条件和不变量。例如一次合法的插入操作要求目标位置可用，成功后文档满足 schema，操作失败时文档保持原状。调用者需要知道自己承担什么，被调用者需要说明保证什么；对外部输入仍需运行时处理，不应仅用断言或类型要求用户永不出错。验证正常和不满足前置条件的路径，并判断契约检查放在哪一层。

**纯核心、效应边界**是一种有用的组织方式：先把不依赖外部环境的规则表示为输入到结果的转换，再在边界执行保存、通知或 DOM 更新。其收益是规则容易以固定输入验证；代价是可能需要传递更多上下文或构造中间结果。若规则高度依赖编辑器事务，强行复制整棵文档以追求形式上的纯粹可能得不偿失。选择前比较真实依赖、内存成本及调用方复杂度。

### SOLID：判断职责与依赖，而不是拆分指标

| 原则         | 实际判断                                           | 常见误用                                 |
| ------------ | -------------------------------------------------- | ---------------------------------------- |
| 单一职责 SRP | 哪些变化原因必须共同维护？不相关变化是否彼此牵连？ | 一个类只能有一个方法，或按行数强拆       |
| 开闭 OCP     | 稳定的变化点能否通过已有契约扩展？                 | 为尚不存在的变化预设插件和抽象层         |
| 里氏替换 LSP | 替代实现是否保留输入、输出、不变量和错误等承诺？   | 只检查类型可赋值，忽略运行行为           |
| 接口隔离 ISP | 调用方是否被迫依赖不使用的能力？                   | 无视实际使用方式，把接口拆得过细         |
| 依赖倒置 DIP | 核心规则是否被具体且易变的外部机制绑住？           | 每个类都配接口，或只反转语法而不改变耦合 |

例如，一个只读存储实现如果满足同样的 TypeScript 接口，却在原契约允许写入时总是失败，就不能在依赖写入能力的地方透明替换。设计可以改为把读取和写入能力分开，也可以让只读失败成为明确契约；具体取决于使用需求。

## 模块边界与接口

### 识别模块及其所有权

以规则和变化原因划分，而不是按技术词汇堆积文件。一个模块应能说明：提供什么能力、依赖什么、拥有和保护什么状态、哪些细节可以独立修改、调用方必须遵守什么条件。内部实现变动若总要求调用方修改，边界可能泄漏；一次功能修改若要同步改多个无关模块，规则可能分散。

模块化不是创建目录或接口的数量。把一个大文件拆成多个相互修改对方内部状态的小文件，并没有消除耦合。共享代码按业务含义和所有权组织，避免在笼统的 `utils` 中堆积互不相关的规则。

**示例：内容计数。**如果某个工具栏只需要当前字数，接口可以提供“读取当前字数”；不应要求工具栏理解编辑器内部树的遍历、缓存失效和事务顺序。若调用方确实需要遍历树，应另行提供受支持的文档访问能力，而不是假设永远不会有该需求。

**验证**：分别替换内部存储、增加一种调用方、模拟失败与销毁，观察公开契约是否仍能满足；检查依赖方向和修改范围。对尚未存在的变化，不以能否实现假想扩展作为唯一评价。

### 设计公开契约

接口需明确输入和有效范围、输出和所有权、副作用、错误、调用时序、并发与取消、兼容性。类型能表达一部分，运行时文档和测试需要补充类型无法保证的行为。默认用法要直接；高级能力在有真实需求时开放，扩展点要有清晰的注册、冲突、执行顺序、失败隔离和清理约定。

**案例：上传边界。**编辑器需要用户选择文件并得到可插入的地址；具体存储和认证可由宿主提供。若开放 `upload(file, signal)`，应定义取消、失败、是否可能重复调用、返回值校验，以及编辑器销毁或文档切换后结果如何失效。接口本身不能保证服务端取消写入，也不能替代服务端授权。

接口越宽，潜在调用方式和兼容成本越大；过窄又会迫使调用方绕过边界。以真实使用场景及变更成本权衡。设计替代实现时验证正常结果、错误、时序和释放行为，而非只验证能编译。

### 抽象的收益和成本

在以下情况考虑抽象：多个调用方依赖同一业务规则；存在明确且需要隔离的变化点；复杂约束需要由模块集中维护；外部机制阻碍核心规则的验证。抽象应减少调用方需要知道的细节。

反过来，只有一处简单实现、需求尚不明确、接口必须暴露全部内部步骤，或者每次修改都需穿过多层转发时，直接代码可能更好。可先保留局部重复，等共同语义和变化方向清楚再抽取。

## 组件库 API 与开发者体验

组件库有两层使用者：接入应用的开发者，以及最终操作界面的用户。API 的名称、类型、默认行为、文档、错误和升级路径共同构成开发者体验（DX）；界面交互见[用户体验与交互设计](#用户体验与交互设计)。API 即使类型正确，如果接入方无法预测状态归属或失败后如何恢复，仍然难用。

需要对照项目实际行为时，先看[受控内容与程序替换](#api-案例一受控内容与程序替换)和[动态集成与异步任务](#api-案例二动态集成与异步任务)，再按接口类型参考[组合、扩展与评审](#api-组合扩展与评审)。

### 按接入旅程设计

从真实接入任务出发，依次考虑：安装与导入、最小初始化、数据读写、常见配置、错误处理、释放资源、调试和升级。让默认路径满足主要场景；高级能力逐步暴露，避免把常用功能藏在大量配置后，也避免为了少数高级场景让所有调用者承担复杂性。

检查可发现性和一致性：相关操作是否能从名称、类型提示和文档中找到；同类操作是否使用一致的术语、参数和错误语义；默认值是否明确且不会悄悄丢失内容；完成任务是否必须依赖内部 DOM、私有字段或调用顺序。API 的简洁应由实际调用方代码和行为判断，不能只数方法数量。

**示例：插入外部内容。**常用场景可能只需要配置一个选择回调；复杂场景可能需要取消、搜索和错误处理。先说明默认行为及失败路径，再决定是否增加扩展接口。不要为了让签名短而隐去文件所有权、回调次数或异步结果失效规则。

例如，假设某个构造函数允许指定只读和自动聚焦，`createEditor(element, true, false)` 很难从调用处看出两个布尔值的含义；具名配置 `createEditor({ element, readOnly: true, autofocus: false })` 更容易识别。这只是接口形状示意，不代表项目当前 API；真实设计还要明确省略选项时的默认值、配置变化是否生效，以及只读是否影响所有命令。只有少量稳定、含义明显的参数时，不必为了形式统一而强制使用对象。

**验证**：从空项目按文档完成最小接入，再实现受控内容、错误处理及销毁；观察是否需要猜参数、查源码或复制私有代码。让不了解实现的接入者按任务尝试，记录失败与理解偏差；演示能运行不等于真实用户已经验证易用性。

### 公共表面和兼容性

明确哪些包入口、类型、组件、命令、事件、CSS 入口和样式变量是公开契约，哪些是内部实现。按语言和生态约定设计名称及类型；相关方法的返回值、错误、同步或异步语义应可预测。公开的类型声明、运行时代码和文档必须一致；TypeScript 的类型提示不能替代运行时校验。[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) 提供命名、可预测性和互操作性的参考，但其中 Rust 专属惯例不能直接套用到 TypeScript。

| API 选择         | 适用情况                     | 需要明确或验证                         |
| ---------------- | ---------------------------- | -------------------------------------- |
| 函数调用与返回值 | 一次请求需要结果，调用链明确 | 失败、同步或异步、返回值所有权         |
| 回调与订阅       | 宿主需响应可重复的事件       | 触发条件、顺序、重入、退订、异常传播   |
| 配置对象         | 选项相关且需要具名调用       | 默认值、互斥项、运行中变更是否生效     |
| 实例方法与命令   | 对特定实例执行操作           | 创建和销毁时机、调用前提、不可执行结果 |
| 扩展或插件       | 存在真实的独立扩展需求       | 注册顺序、能力范围、冲突、版本和清理   |

配置中的值需要区分省略、显式空值和关闭功能；不以一个未经说明的 `false` 或空字符串承载多种语义。对于返回对象，明确是快照、只读视图还是共享可变引用；返回的清理函数、取消信号和资源分别由谁拥有。

变更时把类型兼容、运行时行为、数据格式、CSS、事件时序和宿主代码一起纳入评估。例如修改默认值或把同步回调改为异步，即使签名不变，也可能破坏调用方。若项目采用语义化版本，须结合其公开 API 和版本阶段判断，`0.x` 不应被误写为已承诺稳定；版本号不能替代迁移说明和兼容性测试。

### 框架、构建和生命周期

框架适配器应对齐框架习惯，同时让核心行为在不同框架中保持一致。明确受控和非受控模式各自的权威状态、回写和外部替换语义；不可静默地维护两份互相竞争的内容。回调、配置变化、实例引用和卸载清理应有可观察的契约；多个实例和重挂载不能共享不应共享的会话资源。

运行环境与构建也是接入体验：说明支持的运行时、服务端渲染限制、必要样式、依赖关系和导入方式。公共入口、子路径导出、实际文件、类型声明与 CSS 产物需一致；在真实消费方中通过包入口验证，不只从源码相对路径导入。避免假设所有打包器都以相同方式处理副作用、样式或模块格式。[TypeScript 声明文件发布指南](https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html) 可用于核对声明的分发方式。

**验证矩阵**：对受影响框架分别检查首次挂载、默认和受控内容、宿主回写、配置更新、错误、卸载、重新挂载及多实例；检查从构建产物或打包结果导入的运行时代码、类型和 CSS。按实际变更范围选择，不把未运行的框架测试报告为通过。

### 文档、反馈与 API 评审

每项重要公开能力应解释用途、参数、默认值、返回值、错误、生命周期和兼容约束，给出可运行的最小示例与必要的失败示例；将内部术语翻译成调用者要完成的任务。示例使用公开入口并随 API 验证；迁移指南说明旧行为、新行为、受影响场景与迁移步骤。

设计评审时以调用方代码为证据：是否能正确完成主要任务，误用是否易于发现，错误是否可定位，是否有不必要的重复配置或隐藏副作用，未来变化会破坏什么。收集真实接入反馈或可复现的使用问题；指标如首次成功接入时间只能在定义受试者、任务和环境后解释，不能单独代表整体体验。

### API 案例一：受控内容与程序替换

**场景与目标。**宿主把编辑器内容保存在应用状态中；用户编辑后，应用收到快照并回写 `content`。应用也可能主动恢复一份已保存的内容。设计需要区分用户修改、同一内容的回写、程序替换以及切换到另一篇文档。

**方案比较。**以下是可以选择的语义，不代表所有库都应相同：

| 方案                                  | 收益                             | 成本与适用边界                                             |
| ------------------------------------- | -------------------------------- | ---------------------------------------------------------- |
| 每次程序写入都触发变化事件            | 外部监听者能通过单一事件观察写入 | 受控回写可能循环；需要区分来源和抑制重复                   |
| 事件携带 `user` / `programmatic` 来源 | 监听者可以区分来源               | 来源必须覆盖组合操作、插件和异步回调，契约更复杂           |
| 程序写入不触发用户变化事件            | 宿主回写路径简单                 | 应用不能依赖该事件确认自己的写入；错误和完成状态须另有约定 |

**Semlo 当前依据。**现有[控制器 API](site/controller-api.md#setcontentcontent)、[框架 API](site/framework-api.md#内容更新与文档切换)和[替换实现](../packages/core/src/editor/content/replace.ts)给出以下语义；这里整理为设计案例，具体变更仍应检查当前源码与测试：

| 操作                             | 应观察的契约                                                                     | 接入方需要知道什么                                        |
| -------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 用户编辑                         | 框架组件通过变化事件提供快照                                                     | 应用负责决定何时以及怎样持久化；事件不代表已经保存        |
| 以相同规范化内容回写             | 不重复替换，也不重复通知变化                                                     | 不能仅用对象引用相等判断内容是否相同                      |
| 程序调用 `setContent` 替换       | 不触发 `onChange`；无效内容由 `onError` 报告                                     | 返回类型是 `void`，不能把正常返回当成所有情况下已成功保存 |
| 同一实例提交前重入并替换不同文档 | 可抛出 `ReentrantTransactionError`；提交被销毁打断可抛 `TransactionAbortedError` | 调用方捕获异常；不要在未提交的回调中同步重试              |
| 切换另一篇文档                   | 接入文档建议先保存，再按文档身份重新挂载实例                                     | 区分同一文档回写与跨文档切换，避免沿用不属于新文档的历史  |

需要区分替换结果时可使用 `trySetContent()`；它只报告同步返回时的状态，不代表持久化完成。旧 `setContent()` 的返回类型和事务异常契约不变，具体状态见[控制器 API](site/controller-api.md#trysetcontentcontent)。

一个基于实际公开入口的 React 接入片段：

```tsx
import type { EditorContent } from "@semlo-editor/core";
import { SemloEditor } from "@semlo-editor/react";
import { useState } from "react";

import "@semlo-editor/core/style.css";

export function ArticleEditor({ initialContent }: { initialContent: EditorContent }) {
  const [content, setContent] = useState(initialContent);
  return (
    <SemloEditor
      content={content}
      onChange={({ json }) => setContent(json)}
      onError={(error) => console.error(error)}
    />
  );
}
```

这里的 `content` 只是应用内状态，示例不包含持久化，也不把 `onError` 当成捕获所有创建异常的机制。如果 `initialContent` 代表另一篇文档，宿主需要先处理旧内容，再明确重置此状态及实例；例如按文档身份重新创建包含该状态的组件。不能只改 `initialContent` 而假定 `useState` 会自动重新初始化。Vue 和 Solid 的实际事件与示例见[框架适配](site/frameworks.md)。构建器需要支持 CSS 导入；如果 TypeScript 报告找不到样式模块，应按应用工具链提供 CSS 类型声明，项目体验页的[声明文件](../demo/assets.d.ts)是一种做法。

**验证方法。**在核心及受影响框架中检查：用户输入一次只产生符合约定的变化；把回调快照回写后不重复替换；程序替换不触发该回调；无效输入、事务重入与销毁中断分别走正确错误路径；两个实例互不影响。还要检查内容、选区和历史是否符合各场景要求，不能因为事件次数正确就认为整个交互正确。现有[事务保护测试](../tests/contracts/transaction-guard-formal-candidate.test.ts)和[跨框架快照测试](../tests/adapters/nested-snapshot-framework.test.ts)是具体证据入口；测试文件的存在本身不代表当前运行通过。

**设计启示。**若未来要增加程序写入来源事件，先评估现有宿主对“不触发”的依赖，并比较新增独立事件、扩展事件参数和保持现状的取舍；任何改变都需迁移说明和验证，不因另一套 API 看起来更统一就改变已有契约。

### API 案例二：动态集成与异步任务

**场景与目标。**宿主提供图片上传和提及搜索；运行中它更换搜索提供方，同时已有图片上传尚未完成。接口需要回答：传入对象是局部更新还是整体替换；已开始的工作属于哪个提供方；取消信号是否覆盖网络请求；旧结果能否修改新文档。

| 方案            | 接入体验                         | 风险                                                             |
| --------------- | -------------------------------- | ---------------------------------------------------------------- |
| 整体替换配置    | 状态以传入对象为准，清除能力明确 | 调用方必须同时传入要保留的项；遗漏会清除                         |
| 局部合并配置    | 修改单项方便                     | 必须额外定义如何清除、`undefined` 与缺省的区别，以及并发更新顺序 |
| 每项独立 setter | 每个操作的影响范围清晰           | 多项同时更新时可能暴露中间状态，API 表面更大                     |

**Semlo 当前依据。**[控制器文档](site/controller-api.md#setintegrationsintegrations)将 `setIntegrations` 定义为整体替换；保留的项必须一并传入。已有上传使用启动时的回调；提及搜索提供方变化会中止旧搜索并刷新。图片或附件上传回调的类型只接收 `File`、返回地址；编辑器使旧结果失效不代表自动取消回调内部网络请求，见[集成指南](site/content-and-integrations.md#图片与附件上传)和[类型定义](../packages/core/src/types.ts)。

下面的 TypeScript 片段展示如何由宿主保存**完整**配置后替换搜索能力，而不是只传新搜索回调。它依赖当前公开类型，不代表应用必须采用这种状态管理方式：

```ts
import type { EditorController } from "@semlo-editor/core";

type Integrations = Parameters<EditorController["setIntegrations"]>[0];

export function replaceSearch(
  controller: EditorController,
  current: Integrations,
  searchMentions: Integrations["searchMentions"],
): Integrations {
  const next = { ...current, searchMentions };
  controller.setIntegrations(next);
  return next;
}
```

调用方必须保证 `current` 是自己维护的完整当前配置；若有另一处修改配置，需先协调状态。传入 `{ searchMentions }` 会按现有整体替换约定清除未提供的其他项。该片段不管理宿主请求的取消，也不解决跨应用持久化。

**验证方法。**分别验证新增、替换、清除回调；旧搜索中止或结果失效；旧上传完成时使用约定的回调和文档归属；切换只读、替换文档、销毁与重新挂载；两个实例同时工作。检查网络请求是否真的被宿主取消，而不是仅凭占位消失得出结论。已有[动态集成测试](../tests/contracts/dynamic-integrations.test.ts)可作为测试设计和现有证据入口。

### API 组合、扩展与评审

设计面向宿主的定制能力时，先用一个真实任务比较接口，不预设所有能力都需要暴露：

| 选择              | 适合解决的问题                               | 必须说明的约束                             |
| ----------------- | -------------------------------------------- | ------------------------------------------ |
| 配置项            | 稳定且预期的少量变化，例如是否显示默认工具栏 | 默认值、创建后能否更新、与其他配置的关系   |
| 回调 / 服务提供方 | 宿主负责上传、搜索等外部能力                 | 参数、返回、取消、错误、重入和所有权       |
| 命令 / 控制器     | 宿主主动执行编辑或读取快照                   | 执行前提、选区与焦点、返回值和失败路径     |
| 组合式组件 / 插槽 | 宿主替换部分界面，并承担相应组合责任         | 事件、引用、语义、键盘和焦点如何传递       |
| 插件 / 底层接口   | 稳定扩展机制无法覆盖的高级需求               | 冲突、排序、权限、生命周期、兼容和支持范围 |

组合式界面可以提供更高自由度，也可能把焦点、键盘和语义责任转交给宿主。比如 [Radix 的组合指南](https://www.radix-ui.com/primitives/docs/guides/composition)说明替换底层元素后仍需保证可聚焦和可操作；这用于理解设计代价，不表示 Semlo 已提供该接口。类似地，Tiptap 的[命令](https://tiptap.dev/docs/editor/api/commands)和[内容替换](https://tiptap.dev/docs/editor/api/commands/content/set-content)是对照案例，其事件与默认值不能自动套用到 Semlo。

**评审输出应可核验**：列出典型调用方式和误用、所选择的可替换边界、默认值与生命周期、触发和错误语义、现有接入方兼容性，以及能发现破坏的测试。先通过真实包入口和类型声明验证示例；不要只用内部文件导入来证明公开 API 可用。若某个行为尚无明确约定，标为待决事项，而不是把假设写成现有契约。

## 架构与演进

架构描述重要边界、依赖、数据流和难以改变的选择。名称不能代替对失败、部署、扩展与维护成本的分析。下表是选择起点，不是成熟度阶梯。

| 结构                  | 适用条件                               | 取舍与验证                                       |
| --------------------- | -------------------------------------- | ------------------------------------------------ |
| 分层                  | 展示、领域规则、数据访问职责不同       | 避免无意义的纯转发层；检查是否绕过业务规则       |
| 模块化单体            | 需清楚边界但无需独立部署               | 调试与部署相对直接；需通过依赖和接口维护模块隔离 |
| 端口与适配器 / 六边形 | 核心规则需要隔离外部系统或支持不同实现 | 契约和适配成本增加；验证替代实现与错误语义       |
| 事件驱动              | 多个消费者独立响应事件，或需要异步解耦 | 明确顺序、重复、追踪、订阅生命周期和错误         |
| 管道与过滤器          | 数据经过可理解的处理阶段               | 适合阶段组合；中间格式、失败和性能需要管理       |
| 插件 / 微内核         | 确有独立扩展和可选能力                 | 稳定性、兼容性、权限及资源隔离成为长期责任       |
| 微服务                | 确有独立部署、团队或运行隔离需求       | 增加网络、数据一致性、运维与观测复杂度           |
| CQRS                  | 读写需求确实不同，需要分别建模或扩展   | 要处理投影同步及延迟；不要求同时使用事件溯源     |
| 事件溯源              | 可追溯变化历史或重建状态具有明确价值   | 事件版本、重放、副作用、隐私和迁移都变复杂       |

**编辑器案例。**假设需要支持工具栏与斜杠菜单触发同一插入规则：先确定文档操作是否相同，再把共同的业务规则放在能被两个入口调用的位置；选区保存、焦点恢复和弹层时序可能不同，不应强制共用全部交互。比较直接调用与事件总线时，检查是否真的存在需要解耦的独立消费者；若只有两处同步调用，事件总线可能让调用链更难追踪。

**验证**：分别从两个入口执行、撤销、处理不可插入状态和失焦；检查一个实例销毁不会影响另一个实例。具体行为以当前代码与产品要求为准。ProseMirror 将状态、文档、视图及事务划分为不同概念，可参考其[设计指南](https://prosemirror.net/docs/guide/)，但不能据此假设 Semlo 的所有实现与其相同。

### 领域驱动设计与模型边界

领域驱动设计（DDD）适合业务规则复杂、概念易混淆且需要长期与领域专家协作的场景。它先建立共同语言和明确模型适用范围，再考虑实体、值对象、领域服务及聚合等实现手段。**实体**以身份和生命周期区分，**值对象**主要以值表达含义，**聚合**围绕需要一起维护的不变量定义一致性边界；这些概念不要求一律实现为类或数据库表。

**限界上下文**规定一套模型及术语在哪个范围有效，不同上下文中同一名称可以有不同含义，需要明确翻译关系。它不必一一对应微服务：应用内部也可以有多个模型边界。对于简单数据录入，把每个字段包装成实体或服务反而增加成本。参考 [Microsoft 的领域分析指南](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)。

**案例**：编辑器里的“文档内容”、宿主持久化的“保存版本”、搜索结果中的“摘要”可能代表不同事实。先确认各自的身份、更新和一致性要求，再设计转换；不要仅因为都叫 document 就共用一个可变对象。验证模型能表达用户流程和异常情况，检查跨边界转换是否丢失必要信息。

### 数据一致性与服务边界

先确定一次操作的原子边界、成功标准和失败后可见状态。数据库事务、分布式工作流和 UI 更新并不是同一种原子性。需要跨系统协调时，幂等、去重、重试、补偿和最终一致性分别解决不同问题；补偿可能无法真正撤销外部影响。对服务调用设计超时、有限重试和退避时，先确认操作可安全重试，避免多层重试放大负载。

大规模架构模式只在问题需要时采用；模式目录和适用限制可参考 [Microsoft Cloud Design Patterns](https://learn.microsoft.com/azure/architecture/patterns)。

## 设计模式

设计模式为反复出现的问题提供可交流的方案，并不保证设计合理。评估时先描述变化、参与者和约束，再比较直接实现；确定模式之后，要验证行为契约和失败路径。以下重点展开与组件库较相关的模式，其余模式作为检索入口，不能仅凭名称决定使用。

### 策略与适配器

**策略**将同一职责的不同算法或规则置于统一契约下。适合存在真实的多种实现或运行时选择，例如不同上传策略。收益是调用方无需根据具体实现分支；成本是接口、选择、兼容和测试。只有一两个稳定分支且变化不独立时，直接条件判断可能更清楚。验证每种策略对输入、输出、错误和副作用的共同承诺。

**适配器**将已有接口或语义转换为调用方需要的形式。它适合连接外部库、框架和旧格式；成本是转换、丢失信息及生命周期差异。验证不仅要检查参数形状，也要检查错误、事件顺序、取消与资源释放。例如框架包装器应明确谁拥有核心实例，以及卸载时谁清理；不应让适配器悄悄建立第二份冲突的权威文档状态。

### 命令、观察者与状态机

**命令**把请求表示为可调用的操作，可统一从键盘和菜单触发。它适合需要共享操作入口、校验或记录；代价是命令协议和上下文管理。撤销需要逆操作、事务或快照等额外设计，命令对象本身不会自动提供正确撤销。验证不同入口产生相同行为、不可执行条件与历史记录。

**观察者 / 发布订阅**适合变化有多个消费者，且生产者无需直接知道它们。收益是连接更灵活；风险包括回调顺序、同步重入、错误扩散和遗忘退订。若严格需要一个结果，直接函数调用通常更容易推理。验证同一事件的顺序、重复、监听器抛错和注销后不再收到通知；跨进程消息还要考虑投递与重复语义。

**状态机**明确状态、事件及允许的转换，适合上传、交互会话等状态影响后续行为的流程。它能暴露非法转换，但状态太细会产生组合爆炸。验证初始、正常、取消、失败、重复事件及销毁路径；状态图或类型不是运行时正确性的自动证明。

### 创建与结构模式

**工厂 / 建造者**在创建对象需要保证不变量、多步骤装配或选择实现时有用；对简单值直接构造更易读。验证创建失败时已分配资源是否释放，以及对象是否可能以半初始化状态逃逸。

**装饰器 / 代理**在明确契约下给现有能力附加行为或控制访问，例如缓存、日志或延迟加载。要说明包装顺序、错误、所有权，以及是否改变时序或结果；验证叠加包装后的行为。**外观**为子系统提供易用入口，但不能把调用方必须处理的失败隐藏掉。

| 工厂方法 | 将具体产品的创建交给可替换的创建路径，例如按平台创建文件选择器 | 创建变化不真实时引入额外层次           | 返回对象满足公共行为、失败不泄漏资源             |

## 数据建模与类型

### 从不变量出发

数据模型决定哪些状态容易表达。先问：哪些值互斥，哪些可同时成立，哪些字段共同出现，什么状态需要持久化，以及谁维护约束。互斥状态可用可辨识联合表示；能同时存在的状态不应为了类型整齐而硬塞成互斥。

```ts
type LoadState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; value: T }
  | { status: "error"; error: Error };

function describe<T>(state: LoadState<T>): string {
  switch (state.status) {
    case "idle":
      return "未开始";
    case "loading":
      return "加载中";
    case "success":
      return "已加载";
    case "error":
      return state.error.message;
  }
}
```

此模型让成功状态携带结果，并通过 `status` 缩小类型。若产品需要“保留旧数据的同时刷新”，应单独表达该状态，不能简单禁止。修改状态集合时检查所有分支；TypeScript 的辨识联合及穷尽检查机制见[官方文档](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions)。

**验证**：列出允许和禁止的状态组合，逐个测试事件转换；类型检查发现构造或分支问题，运行时测试仍需覆盖真实输入和时序。

### 解析、校验与归一化

外部数据的静态声明不能证明它真实有效。把不可信输入视为 `unknown`，解析后检查类型和领域约束，再转换成内部表示。解析回答“能否读出结构”，校验回答“是否满足要求”，归一化调整表达形式；不要悄悄把损坏的数据变成看似成功的默认值。

下面是一个刻意缩小的例子，规则仅是 ID 非空且版本为非负整数：

```ts
type RecordInput = { id: string; version: number };

function parseRecord(value: unknown): RecordInput {
  if (typeof value !== "object" || value === null) throw new Error("记录必须是对象");
  if (!("id" in value) || typeof value.id !== "string" || value.id.length === 0) {
    throw new Error("缺少有效的 ID");
  }
  if (
    !("version" in value) ||
    typeof value.version !== "number" ||
    !Number.isInteger(value.version) ||
    value.version < 0
  ) {
    throw new Error("版本必须是非负整数");
  }
  return { id: value.id, version: value.version };
}
```

该例不定义未知字段、长度上限和安全策略，也不代表 Semlo 的内容 schema。实际解析器需明确这些约束，并根据兼容要求决定拒绝、保留或迁移未知数据。验证缺失、空值、错误类型、边界值和旧版本；不要假设 `as RecordInput` 做了任何运行时校验。

### 所有权、共享与派生

每份事实应有权威来源，其他表示是派生、缓存还是快照必须明确。可派生值通常按需计算；为性能缓存时定义更新、失效及错误恢复。浅拷贝不会复制嵌套对象，`readonly` 也不自动冻结运行时数据。共享可变状态时明确可修改者与生存期；数据量大时以性能证据权衡复制与受控修改。

**案例：选中数量。**若 `selectedCount` 只用于显示当前选中列表长度，可以从列表计算；若显示的是提交时快照，或计算成本高到需要缓存，则需单独保存并说明何时更新。验证增删、替换和清空时两个表示不会违反对应约定。

## 函数与控制流

### 命名、输入输出与职责

名称表达业务含义和实际行为：读取、创建、修改、发布及释放不应混称。作用域越大，名称越需要上下文；局部 `index` 可能已足够。函数应让调用方知道输入、输出、前置条件和可观察副作用；参数过多时按领域概念组合，而不是用没有约束的万能对象。

函数保持一个清楚的目的，主流程使用相近的抽象层次。提取代码要形成可命名的概念、隐藏实现或集中同一规则；只为减少行数而拆成多个一行函数，可能使阅读者不断跳转。先判断是同一规则重复还是碰巧长得相似，再决定是否合并。

### 条件和边界

```ts
type User = { id: string; role: "admin" | "member" };
type EditableDocument = { ownerId: string; locked: boolean };

function canEditDocument(user: User, document: EditableDocument): boolean {
  const isOwner = user.id === document.ownerId;
  return user.role === "admin" || (isOwner && !document.locked);
}
```

这个假设规则让管理员可编辑，文档所有者在未锁定时可编辑；只有这些确实是需求时才成立。提取名称有助于集中授权规则，但不能代替服务端授权。至少验证管理员、所有者、非所有者及锁定组合；确认管理员是否应该绕过锁定，而非默认为真。

前置条件失败可提前返回以降低嵌套，但多个出口仍须满足清理和状态约束。不要为简化表达改变短路求值或调用顺序；对 `0`、空字符串、`false`、`null` 和 `undefined` 的处理应符合各自语义，而非统一当作缺失。

### 算法、复杂度与不变量

选择算法前定义输入规模、顺序和正确结果；检查空输入、重复值和边界，并说明循环或递归每一步维持什么不变量、为何会终止。时间复杂度和空间复杂度描述增长趋势，实际成本还包括数据布局、分配、I/O 和运行环境。

例如，去重时先确定是否保留首次出现顺序、如何定义相等、是否区分大小写以及是否允许修改原数组。若按键建立 `Set`，必须保证键的等价关系符合需求；对象引用相等不代表结构相等。验证空集合、重复项、顺序和特殊值，再在代表性规模测量，不以某种数据结构天然“更快”为结论。

### 集合、数值与时间

选择数组、映射或集合时考虑顺序、唯一性、查找和更新方式，以及实际数据规模。线性查找可以比维护额外索引更简单；大量重复查找可能值得索引，但需处理同步与内存。数值计算考虑溢出、精度、取整和单位；金额通常需要明确精度与舍入规则，不能简单依赖浮点相等。

时间点、日历日期、时区和持续时间不是同一概念。跨时区、夏令时、月底和闰日涉及业务定义；固定 24 小时并不总等于当地日历上的一天。验证以实际时区和边界样本为依据，不能仅用开发机器当前时间测试。

## 错误与副作用

### 设计失败契约

区分可预期的业务结果、输入错误、暂时性外部故障和程序不变量损坏。调用方需要按类别处理的失败，可以用显式结果表达；无法在当前层处理的异常应保留上下文向上传递。不要静默吞错、将失败伪装为成功，或把所有异常都转换成空数据。

```ts
type RenameResult = { ok: true; name: string } | { ok: false; reason: "empty" | "too-long" };

function validateName(input: string): RenameResult {
  const name = input.trim();
  if (name.length === 0) return { ok: false, reason: "empty" };
  if (name.length > 80) return { ok: false, reason: "too-long" };
  return { ok: true, name };
}
```

这里的 80 只是示例规则；生产代码应确认字符计数方式、国际文字和产品约束。写入失败是另一层的问题，不能把校验成功当作保存成功。处理外部错误时可补充操作上下文，同时保留原始原因；日志和错误消息不应泄露令牌或用户内容。

**验证**：构造每种拒绝、依赖失败与成功结果，检查调用方的用户反馈和恢复方式；确实需要重试时测试重复提交。异常和显式结果没有普遍优劣，应考虑语言习惯、失败频率以及调用方是否必须处理。

### 副作用的边界与顺序

网络、存储、DOM、时间、随机数及共享状态都可能影响可重复性。将计算与执行区分，有助于单独验证规则，但不应因此建立无意义的层。执行多个步骤时写清先后关系：例如保存失败后是否仍通知、通知失败后保存是否保留、调用方如何得知部分成功。不要用一个“发布成功”掩盖部分失败。

对于不可逆副作用，先验证必要条件，再执行操作；后续失败如何恢复需要明确策略。仅改变代码顺序可能改变事件、历史或宿主回调的可观察行为，重构前应识别这些契约。

## 并发与生命周期

### 异步结果归属

请求发出的顺序不保证完成顺序。先明确目标是最新结果生效、按序执行、全部保留还是合并；不同目标需要不同机制。每次等待之后，都要重新判断实例、文档、选区、权限或会话是否仍有效。取消请求可以节省工作，但不保证远端副作用已撤销；不能只依靠取消来证明旧结果不会应用。

以下示例为每个搜索会话单独维护代次，同时尽力取消旧请求。`fetchResults`、`publish` 和 `reportError` 由使用方提供：

```ts
function createSearchSession<T>(
  fetchResults: (query: string, signal: AbortSignal) => Promise<T[]>,
  publish: (results: T[]) => void,
  reportError: (error: unknown) => void,
) {
  let generation = 0;
  let controller: AbortController | undefined;
  let disposed = false;

  async function search(query: string): Promise<void> {
    if (disposed) return;
    const current = ++generation;
    const previous = controller;
    const request = new AbortController();
    controller = request;
    previous?.abort();
    if (disposed || current !== generation) {
      request.abort();
      return;
    }
    let results: T[];
    try {
      results = await fetchResults(query, request.signal);
    } catch (error) {
      if (!disposed && current === generation && !request.signal.aborted) reportError(error);
      return;
    }
    if (disposed || current !== generation || request.signal.aborted) return;
    publish(results);
  }

  function dispose(): void {
    if (disposed) return;
    disposed = true;
    generation += 1;
    controller?.abort();
  }

  return { search, dispose };
}
```

**验证**：让 A 先发后返回、B 后发先返回，确认只发布 B；销毁后让尚未完成的请求成功和失败，确认不发布或报告旧结果；建立两个会话，确认其中一个取消不影响另一个；再验证有效请求的错误确实报告。取消监听器可能同步触发新搜索或销毁，因此还需覆盖这两种重入。示例不定义查询结果合并、重试或服务端撤销，也不保证 `publish` 不会抛错。

### 资源所有权与重入

监听器、定时器、观察器、订阅、弹层及后台任务都需要所有者、释放时机和失败策略。谁创建不一定由谁释放，但交接必须明确。初始化中途失败、重复销毁、回调重入和清理异常可能发生；按资源契约决定是否继续释放后续资源。

```ts
function observeSize(element: Element, onResize: ResizeObserverCallback): () => void {
  const observer = new ResizeObserver(onResize);
  observer.observe(element);
  return () => observer.disconnect();
}
```

调用者负责在不再需要时执行返回的清理函数；若 `observe` 抛错，实际实现还需考虑此前创建的资源。清理不仅是解绑，还应使旧回调和异步结果无法修改已失效对象。验证正常销毁、失败初始化、重挂载及多实例；检查全局监听和共享缓存不会误清理其他实例。

### 输入法、焦点与浏览器

界面事件的语义依赖浏览器、设备和输入方式。编辑器尤其要考虑输入法组合、选区、焦点、粘贴、键盘快捷键和移动端；静态类型与模拟 DOM 不能证明实际交互正确。对受影响路径使用真实浏览器验证，并针对平台差异报告尚未覆盖的范围。W3C 的 [Input Events Level 2 工作草案](https://www.w3.org/TR/input-events-2/) 描述输入事件模型；草案可能变化，实际实现和兼容性需独立验证。

## 数据流、事务与兼容性

### 受控状态与事务

先画清数据从宿主、编辑器、视图到存储的方向，标出权威来源、反馈回写和快照。受控组件可能把编辑器变化回写宿主，再把值传回编辑器；实现需区分真正的外部替换和同一内容的回写，避免循环更新或丢失选区。事务或批处理可把相关状态变化作为一个可观察的操作，但其原子性范围取决于具体实现，不能假定覆盖网络或外部回调。

**案例：插入带上传的图片。**先约定占位符属于哪个文档和实例、上传结果回来后如何定位占位符、用户撤销或删除后结果如何处理、失败能否重试。一次插入是否应进入撤销历史、撤销后能否重做，必须由产品契约和实现决定。测试用户在上传期间撤销、切换文档、销毁实例和重复插入，不应只测上传成功。

### 格式与公共 API 演进

JSON、HTML、公开导出、节点名、属性、CSS 类、事件和存储键都可能被外部依赖。内部重命名不应意外改变这些标识。格式变更前识别旧数据和调用方，明确读取、写出、未知字段、错误、迁移及回滚；涉及版本共存时同时考虑旧读新和新读旧的要求。

**验证**：用有代表性的已有内容完成读取、编辑、输出与再次读取；核对不变量而不只比较字符串。修改 HTML 路径时检查受影响的导入、导出和必要往返；修改核心公开入口时检查声明、构建产物及受影响的框架适配器。具体项目要求见 [AGENTS.md](../AGENTS.md)。

## 安全与信任边界

安全设计从资产、入口、信任边界和可能的滥用路径开始：输入可能来自用户、宿主、网络、导入文件或第三方插件；静态类型和客户端 UI 限制都不能替代服务端授权。按实际威胁选择校验、权限检查、隔离与日志，保留必要的审计信息，同时避免泄露敏感内容。

### 内容和 URL

HTML、文本、属性、URL、CSS 和脚本上下文有不同风险，不能假设一种转义适用于所有位置。导入富文本时，定义允许的节点、属性和 URL 协议，并在恰当边界使用经过验证的解析和清理机制；仅检查字符串前缀通常不足以处理所有编码和解析差异。嵌入外部资源还应考虑权限、隐私和来源策略。

**案例**：若图片地址由上传服务返回，编辑器仍应根据契约判断地址是否可接受；服务端必须独立处理授权、文件类型和存储策略。验证危险协议、错误编码、非法结构、允许的正常 URL 及错误处理，不把“解析成功”当成“安全”。参考 [OWASP XSS 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)。

### 依赖和权限

优先理解依赖的能力、维护状态、许可和实际必要性。限制暴露给插件和回调的权限与数据；更新依赖时检查兼容、构建、供应链风险和必要回归。安全检查不是只在末尾扫描：设计、实现、验证和维护都有相应责任，参考 [OWASP Developer Guide](https://devguide.owasp.org/en/)。

## 质量属性的专项设计

### 性能与容量

先定义工作负载、设备、数据规模、用户操作与目标，再建立基线。测量瓶颈后选择算法、数据结构或减少工作量，比较优化前后的延迟分布、吞吐、内存或包体；区分平均值和尾部表现。大 O 帮助理解规模增长，但不替代常数、分配、浏览器布局和真实交互测量。

**案例：工具栏刷新。**如果每次输入都遍历整个大文档，先用性能分析确认开销和触发频率，再比较增量计算、按需计算或缓存。缓存需附带失效规则和内存成本；优化后验证输入、选区变化、撤销以及复杂文档结果不变。不要为了无测量依据的性能目标引入长期难维护的复杂结构。

### 可访问性与交互

交互设计应考虑语义、可感知状态、键盘可达性、焦点顺序、可见焦点、名称及辅助技术；颜色和动画不能成为唯一的信息来源。工具栏、菜单、弹层和编辑区域的角色、键盘行为与焦点恢复应与所选交互模式一致。

验证时覆盖鼠标、键盘、屏幕阅读器和适当的移动设备，关注禁用、打开、关闭和错误状态。自动检查能发现一部分问题，不能证明完整可用性；按适用标准评估，参考 [W3C WCAG](https://www.w3.org/WAI/standards-guidelines/wcag/) 和 [ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/)。

### 可靠性与可观测性

定义故障边界、超时、资源限制及恢复策略；对于服务，监测真实用户影响和关键依赖，不只记录内部函数调用。区分错误率、延迟和可用性目标，说明测量窗口和数据来源。重试、熔断、隔离和降级各有适用条件，不应机械叠加。对于离线组件库，宿主可观测能力和隐私边界也要明确，不能假设有服务端监控。

## 用户体验与交互设计

UX 关注用户完成任务的全过程，包括理解、操作、反馈、出错与恢复；视觉样式和无障碍是其中的重要部分。设计应根据使用者、场景和证据权衡，而不是把所有屏幕都套成同一套模板。[Nielsen Norman Group 的可用性启发式](https://www.nngroup.com/articles/ten-usability-heuristics/) 可用于发现潜在问题，但启发式检查不能代替真实用户研究。

需要具体交互方案时，先看[链接插入](#ux-案例一链接插入的完整路径)、[上传反馈与恢复](#ux-案例二上传期间的状态和恢复)，以及[界面定制契约](#组件库中的界面组合与定制契约)和[用户体验验证示例](#用户体验验证的可执行示例)。

### 从用户任务和情境出发

明确目标用户及其经验、设备、输入方式、能力差异和使用环境；识别高频任务、关键决策和错误后果。例如编辑器中的连续写作、选择格式、插入内容、查找与撤销，不一定需要相同的界面优先级。按“触发—理解—操作—反馈—完成或恢复”描述路径，区分首次使用和熟练使用。

通过访谈、任务观察、已有反馈和适用的产品数据形成假设；资源有限时先验证影响大、风险高的假设。不要把设计者的偏好当作用户事实，也不要凭一位测试者或一次走查推断所有人。涉及用户内容的研究先考虑授权、隐私及数据最小化。

### 核心交互原则

| 原则           | 设计时判断                                 | 常见取舍与验证                                       |
| -------------- | ------------------------------------------ | ---------------------------------------------------- |
| 状态可见       | 当前操作、加载、保存或失败是否有适时反馈   | 避免每次微小变化都打断；检查慢操作、失败与恢复       |
| 用户掌控       | 能否取消、退出、撤销或理解不可逆后果       | 撤销范围和有效期需真实可靠；不要承诺无法撤回的动作   |
| 一致与可预测   | 同一概念的名称、行为和位置是否一致         | 遵循平台习惯，但不同上下文有真实差异时保留差异       |
| 识别优于记忆   | 用户能否看到相关选项、状态和可用操作       | 过多常驻控件会分散注意；观察用户是否能找到关键功能   |
| 防错与恢复     | 是否能限制无效输入，并在失败时提供下一步   | 过度确认会打断流程；错误保留上下文并允许安全重试     |
| 渐进披露与效率 | 初学者能否完成基本任务，熟练者能否高效操作 | 高级选项和快捷键仍需可发现；测量任务而非仅看控件数量 |

上表是设计与评审的视角，不是每个界面都必须展示进度条、确认框或提示。文案使用用户能理解的领域语言，区分说明、警告和错误；说清发生什么及用户能做什么，避免暴露无意义的内部错误码。

### 组件库界面与宿主协作

编辑器组件既要提供一致的默认体验，也要嵌入不同宿主。明确哪些交互、内容和焦点由组件管理，哪些保存、上传、权限和通知由宿主提供；不要在组件中假定宿主已经保存或网络操作一定成功。提供与产品实际能力相符的视觉状态、空态、加载态、禁用态和错误态。

设计可定制能力时分别考虑主题、密度、语言、布局和品牌：公开稳定的定制入口，并说明其影响范围；不要把私有 DOM 层级当作推荐的长期扩展方式。定制不应破坏对比度、可见焦点和键盘操作；同时要给宿主留出必要的布局和文案控制。对弹层检查遮挡、滚动容器、视口边界与层级，避免组件影响其他实例。

### 编辑交互、焦点与状态

编辑器的文档、选区、焦点和历史直接影响用户感知。相同命令从工具栏、快捷键或菜单触发时，结果应遵循同一业务规则；但不同入口保存选区和恢复焦点的方式可能不同。不能只看按钮是否响应，还要看用户是否能继续编辑、能否撤销、内容是否被意外覆盖。

**案例：插入链接弹层。**先确认用户打开弹层时选中的是文字还是光标、取消是否保留原内容、失效选区如何处理、确定后焦点应去哪里；地址无效时给出可理解的错误并保留用户输入。若采用模态对话框，按其实际语义实现焦点进入、内部键盘操作、关闭及合理的焦点去向；非模态弹层不能仅因外观相似而套用模态陷阱。W3C 的[模态对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 是设计实践，不是对所有弹层的统一要求。

验证正常插入、取消、无效输入、重复提交、选区变化、撤销与重做；用鼠标和键盘操作，并按影响检查触屏、输入法和辅助技术。关闭时原触发元素可能已消失，焦点去向必须结合真实流程处理，而不是机械调用一个失效引用。

### 视觉层次、响应和动效

视觉设计应帮助用户识别内容、操作和状态：用合理的层级、间距、字体、对比和反馈突出当前任务；图标需要在上下文中可辨认，必要时提供文字或可访问名称。避免只用颜色表达错误或状态。检查浅色、深色或宿主主题下的可读性和实际内容，而非只审查静态空白样稿。

响应式行为不仅是缩窄布局：在桌面和手机上考虑可用空间、触达范围、虚拟键盘、滚动、浮层遮挡及输入方式。动效应服务反馈或状态变化，避免阻碍连续输入；尊重用户减少动态效果的偏好，并确认动画结束前后功能可用。不要为了视觉一致性牺牲文本选择、缩放或键盘导航。

### 验证与迭代

先确定任务、参与者和成功条件，再选择启发式评审、可用性测试、无障碍检查、原型比较或线上指标。观察用户能否独立完成任务、是否误操作、卡在哪里及如何恢复；任务完成率、耗时与错误率必须附带样本、场景和方法，不作为脱离上下文的质量分数。访谈、走查和任务测试提供不同类型的证据，不能仅凭访谈或评审推断用户完成任务的表现；任何单一方法都有覆盖范围。

设计变更后在真实浏览器检查桌面、受影响的移动端、键盘与焦点，并在需要时邀请使用辅助技术的人参与；自动化扫描只能发现部分问题。W3C 的 [WCAG 四项原则](https://www.w3.org/WAI/WCAG22/Understanding/intro) 和 [ARIA 实践指南](https://www.w3.org/WAI/ARIA/apg/about/introduction/) 可分别用于理解可访问性要求与常见交互模式，实践指南本身不是符合性标准。记录未验证的设备、浏览器和人群，不宣称全面可用或合规。

### UX 案例一：链接插入的完整路径

**用户任务。**用户选中已有文字，或在空光标处，通过工具栏、快捷键或斜杠入口插入链接；完成后继续写作。设计必须处理选区、文本格式、地址、焦点、取消与撤销之间的关系。

**方案比较。**以下是可讨论的设计选项，并非对现有行为的改动决定：

| 方案                               | 交互结果                                       | 代价与需确认的问题                                 |
| ---------------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| 弹层内保留草稿，确认后才写入文档   | 取消时通常不产生文档修改                       | 需保存或重新映射目标选区；文档变化后目标可能失效   |
| 打开时先插入或标记占位，稍后补地址 | 能立即体现将要插入的内容，适合某些连续编辑流程 | 关闭弹层后占位如何呈现、何时删除、如何撤销必须明确 |
| 直接根据输入即时更新文档           | 反馈及时                                       | 输入无效、撤销粒度和自动保存可能更复杂             |

**Semlo 当前可核验的例子。**[链接会话源码](../packages/core/src/editor/url-session.ts)在部分新建链接路径中先创建未设置地址的链接占位或标记；[浏览器回归场景](../tests/browser/cases/browser-links.ts)对斜杠入口规定：按 `Escape` 关闭后保留未设置地址的“链接”占位，再撤销可恢复斜杠。这个例子表明“取消”与“文档完全不变”不是天然同义词；不能据此推断所有入口或所有取消方式完全相同。

| 步骤                 | 观察与设计问题                         | 可验证结果                                         |
| -------------------- | -------------------------------------- | -------------------------------------------------- |
| 选中文字并打开       | 如何保存目标，是否保留已有文字格式     | 弹层文本与选区一致，完成后格式不丢失               |
| 空光标打开           | 采用默认文本、空草稿还是阻止提交       | 明确默认值、输入要求和确认行为                     |
| 输入地址             | 接受哪些协议及相对地址，如何说明错误   | 合法输入可提交；无效输入保留上下文并提供可理解反馈 |
| 取消或外部关闭       | 是撤销草稿、保留占位还是保留已完成内容 | 分入口检查结果、焦点去向和后续撤销                 |
| 提交后继续写作       | 如何恢复焦点及选区，历史如何分组       | 能继续输入；按约定撤销、重做，不意外修改其他实例   |
| 文档、权限或实例变化 | 打开的弹层和保存的目标是否仍有效       | 不向失效文档提交；关闭或禁用行为有明确反馈         |

源码中的地址处理支持的输入范围与错误提示文案应一起评估：当前链接分支接受 HTTP / HTTPS、`mailto:` 和部分相对地址；无效输入提示用示例说明可接受的地址，而不把示例写成完整范围。修改支持的地址类型时，应同时验证提示、实际提交和既有内容兼容性。

**可访问性交互。**先确定它是模态对话框、非模态弹层还是其他模式，再选择键盘与焦点策略。`role="dialog"` 本身不意味着模态；只有确实限制外部交互的组件才能按模态要求处理。按入口检查 `Tab`、`Escape`、焦点可见、关闭后目标消失的情况、错误的可感知方式，以及输入法组合期间按键的处理。参考 [W3C 模态对话框实践](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)，实际实现和辅助技术组合仍需验证。

**验证方法。**从已有浏览器场景出发，增加或选择与改动相关的路径：选中/空光标、新建/编辑已有链接、各入口、合法/非法地址、确认/取消、文档改变、只读切换、撤销与重做、两实例隔离。真实浏览器检查鼠标、键盘及受影响的移动端；输入法和屏幕阅读器需在目标环境单独验证，不能由自动化单独证明。

### UX 案例二：上传期间的状态和恢复

**用户任务。**用户插入图片后继续编辑，同时上传可能成功、失败或仍在进行。用户需要知道当前发生什么、能否继续、文档何时拥有可保存的地址，以及切换文档或权限时会怎样。

当前[接入指南](site/content-and-integrations.md#图片与附件上传)说明上传期间存在占位，替换文档、销毁或切换只读后旧结果不会写入新文档；它也说明接入方网络请求不会因此自动中止。对于“显示什么进度”“允许怎样重试”或“何时保存”的细节，必须根据对应功能实际契约确认，不能从一般原则推断。

| 情境                   | 设计选择                                     | 取舍与验证                                                   |
| ---------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| 进行中                 | 仅表示等待，或展示可获得的真实进度           | 回调未提供进度时不能伪造百分比；检查继续输入与占位映射       |
| 失败                   | 保留错误上下文并提供可行操作，或交由宿主反馈 | 明确错误属于组件还是宿主；重试需要可用文件和权限             |
| 用户撤销或删除占位     | 取消任务、忽略结果，或保留可恢复草稿         | 外部请求和上传副作用未必能撤回；验证无错误插入               |
| 切换文档 / 只读 / 销毁 | 让旧结果失效，必要时由宿主取消请求           | 分别验证当前实例、文档、用户提示及服务端副作用               |
| 持久化                 | 等待完成，或允许保存包含占位的草稿           | 由产品定义可恢复数据及提示；不能把占位误称为可长期访问的图片 |

这些是设计备选和验证问题，不是已全部实现的能力。设计记录至少说明组件与宿主各自掌握的状态、用户看到的反馈、失败后的恢复以及无法撤销的外部副作用。

### 组件库中的界面组合与定制契约

对主题、布局、快捷键、工具栏和弹层定制，分别定义**组件负责什么、宿主可以替换什么、替换后谁负责什么**。例如允许宿主提供按钮时，应考虑事件和引用是否透传、禁用与忙碌状态是否一致、可访问名称与焦点由谁提供；允许覆盖颜色时，要检查文字、焦点和不同状态在实际主题下是否仍可辨认。若项目尚无此扩展点，应把它作为候选而非现有 API。

对比完整默认界面、受支持的局部定制与完全自定义界面：默认界面上手快但自由度有限；局部替换需要稳定的组合边界；完全自定义更灵活，但宿主要负责更多交互和无障碍细节。不要为了某个想象中的定制场景提前暴露内部 DOM，也不要把宿主确实需要的能力藏在私有选择器中。

**验证方法。**在默认主题与至少一个真实宿主约束下检查样式隔离、层叠和弹层定位；检查窄视口、长文本、系统字体变化、键盘及缩放。若提供组合扩展，使用一个独立消费方替换控件，验证事件、禁用、焦点和名称；自动检测与人工辅助技术检查互补，不把其中任一项当成全面无障碍证明。

### 用户体验验证的可执行示例

以“为选中文字添加链接并继续输入”为任务，邀请符合目标使用场景的参与者，从普通文档起步，不预先指出按钮位置。观察能否发现入口、是否理解文本和地址、是否知道失败后怎样修正、完成后焦点是否符合预期，以及误操作后是否知道怎样恢复。可分别给键盘和触屏使用者设计等价任务；记录设备、浏览器、输入方式、前置经验、样本和任务，不记录不必要的文档内容。

将结果区分为观察事实、参与者反馈、设计推测和改动建议。例如“某次测试中按 Escape 后占位仍在”是观察；“所有用户都会误解取消”需要更广证据。对任务完成、误操作和耗时进行汇总时说明样本与条件，不以一次走查或单个指标证明整体体验。未邀请真实用户或未覆盖辅助技术时，应明确写出尚未验证的范围。

## 综合案例：为编辑器增加异步内容选择

这个假设案例展示如何把宏观和微观判断连成一条链。它不是项目需求或当前实现的描述。

### 问题与不变量

假设使用者通过工具栏打开选择器，搜索宿主提供的内容并插入当前文档。选择器允许连续输入、取消、重新打开；页面上可以同时存在两个编辑器。

需要先向产品和调用方确认：插入的位置是打开时保存的选区还是确认时的选区；搜索失败如何呈现；空结果是否等同错误；关闭弹层是否取消请求；插入是否可撤销；保存的选区失效后应该拒绝、恢复还是使用当前选区。没有这些答案，代码无法凭模式名称推导出正确行为。

在假设“最新搜索生效、仅当前会话可插入、实例互不干扰”的前提下，可提出三条待验证的不变量：

1. 旧会话、已销毁实例或旧搜索的结果不能更新当前会话。
2. 一次确认最多触发一次符合产品要求的插入；失败不能报告成功。
3. 各实例的选择器状态、宿主能力和资源相互隔离。

### 对比方案

| 方案                           | 优点                               | 代价与适用边界                                                  |
| ------------------------------ | ---------------------------------- | --------------------------------------------------------------- |
| 工具栏直接管理 UI、搜索和插入  | 入口少时实现直接，调用路径短       | 其他入口复用时容易复制规则；界面和会话生命周期容易混在一起      |
| 提取实例级会话，工具栏负责装配 | 把搜索代次、会话失效和确认边界集中 | 需定义接口、回调和释放责任；如果只有简单同步选择，可能多一层    |
| 全局事件总线协调所有实例       | 新监听者可订阅事件                 | 需额外证明事件归属、顺序和清理；对单一请求-结果关系可能过于间接 |

如果多个入口确实共享同一搜索和确认规则，实例级会话值得考虑；若只有一个简单入口，保留局部实现也可以。无论选哪一种，保存选区与恢复焦点是否共享，要按各入口实际交互判断，不能因追求复用而合并不同语义。

### 一条可能的数据流

宿主提供搜索能力；某编辑器实例创建选择会话；界面把查询交给会话；会话只发布当前代次的结果；用户确认时重新检查实例、文档和目标是否有效；编辑器通过已有操作机制插入；关闭或销毁会使会话和旧结果失效。该流程仅是设计候选，最终顺序及错误处理应由项目契约和源码确定。

### 验证矩阵

- **正常**：搜索、选择、插入、撤销与重做；确认内容、焦点和选区符合约定。
- **顺序**：先请求 A 再请求 B，但 B 先完成；确认 A 不覆盖 B。
- **取消与销毁**：关闭、重新打开或销毁后，旧成功和旧失败均不能改变新会话。
- **隔离**：同时操作两个实例，关闭一个不影响另一个；宿主能力更换后旧请求不得误用新会话。
- **异常**：搜索失败、空结果、重复确认、目标失效和插入失败分别按契约处理。
- **交互**：键盘、焦点恢复和受影响的移动端路径在真实浏览器核查。

测试应观察对外行为并控制异步完成顺序；仅断言内部生成了某个请求 ID 不足以证明旧结果不会显示。若当前需求不包含某项行为，应记录假设或未覆盖范围，不把上述清单变成每个修改的强制流程。

## 验证与评审

### 选择能发现问题的证据

先写出可能被破坏的行为和不变量，再选择验证层次；不以测试数量或覆盖率单独证明正确性。

| 风险或变化         | 候选验证                       | 需要留意                                 |
| ------------------ | ------------------------------ | ---------------------------------------- |
| 局部规则或数据变换 | 单元测试、边界示例、属性测试   | 断言输入输出和不变量；避免只复述实现     |
| 模块接口           | 契约测试、真实依赖的集成测试   | 覆盖错误、顺序、资源和调用方使用方式     |
| 用户流程           | 真实浏览器或端到端测试         | 关注焦点、输入法、移动端和可访问性       |
| 解析器与格式       | 旧内容往返、无效数据、模糊测试 | 定义语义等价；往返一致不代表原始输入安全 |
| 异步与资源         | 控制完成顺序、失败、销毁和重入 | 覆盖过期结果及多实例隔离                 |
| 性能               | 代表性数据和设备上的基线与对比 | 记录测量条件，不从一次运行推断普遍结论   |

**属性测试**用生成的数据验证对一类输入成立的性质，例如某些归一化操作满足 `normalize(normalize(x)) = normalize(x)`；这个性质必须先由规则保证。**模型测试**用简化状态模型比较操作序列，适合复杂状态机；**模糊测试**通过大量或变异输入寻找解析失败和异常。它们不能替代对期望结果的理解，也不能证明所有情况正确。

修复缺陷时，若可行，先构造能重现触发条件的验证，再修复并确认它通过；同时验证邻近行为。快照失败先检查实际差异和行为，再决定是修复还是更新预期。重构应保护外部行为，但若意外行为本身已被调用方依赖，需明确兼容性而不是自行假定无影响。

### 评审与交付

按风险顺序检查：需求与兼容性、正确性和数据安全、状态与生命周期、模块边界、性能和可维护性、验证证据。提出发现时说明触发条件、位置、后果和证据；把确定缺陷、待验证风险和个人偏好区分开。不要仅因为没有使用某种模式或抽象而判定缺陷。

交付时说明实际行为变化、运行过的相关检查及结果、未验证的必要范围和实质限制。对新 API、格式或有成本的架构决定记录背景、备选方案和理由；随实现更新过时文档。检查通过是证据，不等于用户验收或所有场景都正确。
